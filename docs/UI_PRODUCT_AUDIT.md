# INRIUM — аудит інтерфейсу та користувацької логіки

Дата: 2026-10-17  
Обмеження цього документа: **код, БД і конфігурація не змінювались**. Джерела: фактичні файли фронтенду/бекенду, Prisma-схема, `docs/UI_HANDOFF.md`, HTTP-перевірка публічних маршрутів на локальному Docker (`http://localhost:3000`), раніше прогнані Jest/Playwright (див. `docs/TEST_MATRIX.md`).

## Методика статусів

| Статус | Що означає в цьому документі |
|--------|------------------------------|
| **Працює повністю** | Є UI + відповідний API/guard; поведінка підтверджена тестами або HTTP/браузером, без відомих розривів сценарію. |
| **Працює частково** | Реалізовано, але є дірки UX, неповне покриття бекенд-контракту або сценарій не замикається зручно. |
| **Заглушка** | Елемент є в UI/моделі, але не виконує заявленої функції або свідомо не завершений (DRAFT legal, порожні контакти без env). |
| **Відсутня** | Функція, очікувана для TTRPG-платформи або заявлена копірайтом, не існує в коді. |
| **Не перевірено** | Потрібні зовнішні ресурси (SMTP, CAPTCHA keys, ADMIN-пароль) або браузерний e2e цього сценарію в цьому аудиті не ганявся. |

Наявність кнопки, `onClick` або endpoint **не** вважається доказом «Працює повністю».

## 1. Повна карта сайту

### 1.1. Публічні сторінки (гість)

```
/                      головна (блоки з CMS)
/news                  стрічка новин
/articles              статті
/systems               каталог ігрових систем
/systems/[slug]        картка системи
/help                  список довідок
/help/[slug]           сторінка довідки
/content/[slug]        універсальний матеріал (новина/стаття)
/games                 каталог ігрових сесій
/games/[slug]          картка гри + заявка
/communities           каталог спільнот
/communities/[slug]    сторінка спільноти (текст + обкладинка)
/users/[id]            публічний профіль (ім’я, роль, біо, дата)
/search                пошук CMS (не ігри)
/about /contacts /advertise
/privacy /terms        юридичні чернетки DRAFT
/robots.txt /sitemap.xml
```

Навігація шапки (`apps/frontend/src/components/Header.tsx`): Новини, Статті, Ігрові системи, Ігри, Спільноти, Довідка, іконка пошуку, Про нас / Реклама / Контакти (верхня смуга). Футер дублює ці розділи + legal. Розділ наборів (`/kits`) вилучено з продукту.

### 1.2. Автентифікація

```
/login                 cookie-вхід, CAPTCHA за збіркою, resend verify
/register              реєстрація без автологіну
/forgot-password       запит скидання (нейтральна відповідь)
/reset-password        новий пароль за ?token=
/verify-email          підтвердження за ?token=
```

### 1.3. Кабінет (сесія)

```
/profile                         профіль, пароль, заявки-прев’ю, закладки, self-delete
/my/applications                 усі заявки гравця
/my/games                        список ігор GM/ADMIN
/my/games/new                    створення гри
/my/games/[id]/edit              редагування + обкладинка
/my/games/[id]/applications      заявки: approve/reject/remove
```

Guards: `ProtectedRouteShell` + `useProtectedRouteGuard` (`AUTH` або `GAME_MASTER_OR_ADMIN`). Анонім отримує клієнтський редірект на `/login?next=…` (HTTP самої сторінки лишається 200 — оболонка RSC).

### 1.4. Адмінка

```
/admin                   дашборд + реальні лічильники GET /admin/stats
/admin/content[ /new | /[id]/edit ]
/admin/systems[ /new | /[id]/edit ]
/admin/home-blocks       увімкнення секцій головної
/admin/users             ADMIN: пошук, зміна ролі
/admin/communities[ /new | /[id]/edit ]   ADMIN
```

**Немає** `/admin/settings`, `/admin/games`, черги модерації ігор. Адмін бачить чужі ігри через `/my/games` (`GamesController.listMyGames` для `ADMIN` повертає всі).

Ролі (`schema.prisma` `UserRole`): `PLAYER` | `GAME_MASTER` | `EDITOR` | `ADMIN`. Статуси акаунта `ACTIVE|BLOCKED|DELETED` є в БД; **змінити статус з UI неможливо**.

## 3. Користувацькі сценарії за ролями

Легенда прохідності: **можна пройти** / **з тертям** / **обривається** / **немає шляху**.

### 3.1. Гість

| Крок | Прохідність | Коментар |
|------|-------------|----------|
| Головна | з тертям | Працює; акцент на CMS, не на столі. Якщо ігор 0 — секція ховається, гість може не здогадатись, що сесії існують як продукт. |
| Навігація шапка/футер | можна пройти | Усі href існують (HTTP 200). На мобільному nav `whiteSpace: nowrap` + багато пунктів — **очікуваний overflow**, гамбургера немає. |
| Пошук | з тертям | Працює для матеріалів; гра «Дракони о 19:00» у пошуку не знайдеться. |
| Каталог ігор | з тертям | Список є; немає фільтра «набір відкритий» / система / місто / онлайн. |
| Картка гри | можна пройти (читання) | Заявка вимагає логін (`/login?redirect=/games/…`, логін приймає `redirect`). |
| Профілі / спільноти | можна пройти (читання) | Спільнота = стаття без спільноти. |
| Реєстрація → (verify) → вхід | можна пройти локально | Playwright PASS. Production-шлях листа — **Не перевірено** / BLOCKED SMTP. |

### 3.2. Зареєстрований гравець (PLAYER)

| Крок | Прохідність | Коментар |
|------|-------------|----------|
| Вхід, reload, logout | можна пройти | Cookie HttpOnly; e2e. |
| Профіль | можна пройти | Форми з помилками/успіхом/loading. |
| Знайти гру й подати заявку | з тертям | Немає входу «мої заявки» в шапці; після логіну з картки гри `redirect` працює. Немає фільтрів каталогу. |
| Стежити за статусом | з тертям | Треба відкрити профіль або `/my/applications` вручну; немає нотифікацій. Cancel зі списку заявок немає. |
| «Мої ігри» як гравець | обривається коректно | Header не показує; прямий URL → «Доступ заборонено» (`ProtectedRouteShell`). |
| Вийти з гри після approve | немає шляху | Лише майстер remove. |
| Стати GM | немає шляху | Чекати адміна. |

Сценарій «зарєєструвався — знайшов стіл — сів грати» **технічно можливий**, але з зайвими переходами і без супроводу після approve (немає інструкції «як приєднатись до сесії»: Discord/посилання/час у заявці не зберігаються окремими полями — лише `startsAt` гри і вільне повідомлення).

### 3.3. Майстер (GAME_MASTER)

| Крок | Прохідність | Коментар |
|------|-------------|----------|
| Створити чернетку | можна пройти | Після create редірект на edit (обкладинка). |
| Відкрити набір (OPEN) | з тертям | Треба знати, що статус у селекті = публікація; немає прев’ю «як побачить гравець» окремою кнопкою (є посилання зі списку на `/games/slug`, для DRAFT публічний GET не відкриє — очікувано). |
| Заявки approve/reject | можна пройти в UI | Є loading, помилки, confirm на remove. Немає bulk. |
| Склад / FULL | можна пройти | Бекенд синхронізує OPEN/FULL від `maxPlayers`. |
| Завершити / скасувати | з тертям | Знову селект статусу, без окремого wizard. |
| Видалити | можна пройти | confirm у браузері. |

Сценарій GM **замикається**, якщо роль уже GAME_MASTER. Онбординг «я хочу водити» **немає**.

### 3.4. Адміністратор / редактор

| Крок | Прохідність | Коментар |
|------|-------------|----------|
| `/admin` статистика | можна пройти | Реальні count; EDITOR без users. |
| CMS матеріали/системи/набори | можна пройти | Форми + ImageUpload + markdown. |
| Користувачі: видати роль GM | можна пройти | Select + `PATCH /users/:id/role`. Немає підтвердження «останній ADMIN». Бекенд захищає останнього адміна (`users.service.ts` `adminUpdateRole`). |
| Заблокувати користувача | немає шляху в UI | Статус BLOCKED використовується тестами/JWT, не адмінкою. |
| Модерувати гру | з тертям | Через «Мої ігри» під акаунтом ADMIN. |
| Спільноти | можна пройти | CRUD вітрини. |
| Settings / feature flags | немає шляху | Ок як відсутність фейку. |

Редактор **не** керує users/communities (посилання сховані, прямий URL → «Доступ заборонено»). Це узгоджено з backend `@Roles(ADMIN)`.

## 4. Виявлені проблеми UI/UX

### Навігація та IA

1. **Продукт позиціонується як TTRPG-портал сесій, а головна продає CMS.** Hero CTA: системи / статті / набори (`page.tsx` ~177–186). Пункт «Ігри» є в шапці, але не в першому екрані.
2. **У шапці немає «Мої заявки»** для гравця — лише профіль. GM бачить «Мої ігри». Асиметрія.
3. **ADMIN «Мої ігри» = усі ігри платформи** — когнітивний конфлікт.
4. Шапка використовує `<a href>` замість `next/link` — повне перезавантаження (працює, гірший UX).
5. Коментар у Header «Skeleton … localStorage» **застарілий** (сесія з `/auth/me`).
6. Немає мобільного меню; top-bar + 7 пунктів nav + auth на вузькому екрані не складаються.

### Порожні стани та копірайт

7. Блок GAMES на головній при 0 ігор **зникає**; системи/набори показують «скоро з’являться». Непослідовно.
8. `/games` empty: «немає відкритих ігор», хоча API віддає й FULL/IN_PROGRESS/FINISHED.
9. `GameApplyButton` при статусі ≠ OPEN повертає `null` — гравець FULL/IN_PROGRESS не бачить, *чому* не може податись.

### Форми, помилки, loading

10. Більшість кабінетних форм мають error + disabled submit — добре.
11. `BookmarkButton` при помилці тихо робить `refreshCheck` без повідомлення користувачу.
12. Зміна ролі в адмінці — `alert()`, не inline error.
13. `/my/applications` без дій і без refresh після змін на іншій вкладці (треба reload).

### Адаптивність

14. Головна: `gridTemplateColumns: '1fr 1fr'` для новин і `'repeat(3, 1fr)'` для CTA.
15. Footer: `'auto repeat(3, 1fr)'`.
16. GameForm: `'1fr 1fr'` для статусу/гравців.
17. Адмін quick links: `'repeat(3, 1fr)'`.
18. Немає viewport-перевірки в цьому аудиті (код-рев’ю CSS). Статус адаптивності: **Працює частково / ризики на <768px**.

### Логічні розриви FE/BE

19. Каталог ігор не експонує фільтри, які вже є в API.
20. Пошук не покриває головний user-job «знайти стіл».
21. Немає UI блокування користувача при наявному статусі в моделі.
22. Дубль «ігрова система»: `ContentType.GAME_SYSTEM` у CMS і сутність `GameSystem`.

### Битих посилань

23. Перевірені маршрути карти сайту відповідають `page.tsx`. Фейкового `/admin/settings` немає.
24. Клієнтські guarded URL віддають HTTP 200, потім JS-редірект — не 302. Для гостя це короткий кадр «Завантаження…».

## 5. Відсутні та частково реалізовані функції

### Частково

- Каталог і пошук ігор (немає фасетів, пошук ігор відсутній у `/search`).
- Заявки гравця (немає cancel у списку, немає leave, немає нотифікацій).
- Спільноти (вітрина без членства).
- Адмін-статистика (не всі поля API).
- Home blocks (тільки toggle enabled).
- Публікація гри (статус-селект замість сценарію «відкрити набір»).
- Legal/contacts (чесні чернетки / порожні контакти).
- Закладки (немає ігор).

### Відсутні (не видавати за наявні)

Для гравців: карта/онлайн-офлайн, розклад, відгуки про майстра, чат, нагадування, «стати майстром», вихід зі складу, улюблені столи.

Для майстрів: шаблон сесії, recap, приватне посилання для складу, інтеграції (Discord, Foundry), waitlist окремо від PENDING, оплата/донат, повторювані сесії.

Для спільнот: власник, члени, роль модератора, стрічка, прив’язка ігор клубу.

Для адмінів: block/unblock, аудит-лог, модерація описів UGC окремою чергою, скарги, feature flags UI.

Платформа зараз = **CMS портал + мінімальний LFG (looking-for-group)**. Це не «віртуальний клуб із сесіями».

## 6. Технічні обмеження для майбутнього редизайну

Не ламати (див. також `docs/UI_HANDOFF.md`):

- Cookie-only auth, `credentials: 'include'`, заголовок `X-CSRF-Token` (`src/lib/http.ts`).
- Не писати токени в storage; не показувати JWT у UI.
- Обгортка `{ success, data }` і українські `message`/`code`.
- `forbidNonWhitelisted` DTO: імена полів форм = контракт (`CreateGameDto`, `ApplyGameDto`, профіль).
- Публічний список ігор не повинен просити DRAFT; slug GET не відкриває non-public.
- Ролі: PLAYER ≠ create game; EDITOR ≠ users/communities; ownership на mutate гри.
- Markdown без raw HTML (`MarkdownContent`).
- Uploads: JPEG/PNG/WebP, ліміт, `/uploads/…` через `resolveMediaUrl`.
- `safeNextPath` для post-login.
- Legal DRAFT-банер, доки немає затвердженого тексту.
- Контакти тільки з `NEXT_PUBLIC_CONTACT_*`, без вигаданих адрес.

Можна міняти вільно: верстка, копірайт (крім legal/auth помилок без узгодження сенсу), порожні стани, порядок блоків головної (дані все одно з `home-blocks`), картки, адаптив, підписи статусів (`labels.ts` / `game-labels.ts`).

Архітектурний борг, який редизайн не «замалює»: два типи «систем», невикористаний `Game.systemId`, CUSTOM-блок, in-memory rate limit (не UI).

## 7. Пропозиції щодо структури сайту та навігації

Рекомендована інформаційна архітектура **як напрям**, не як зроблена робота:

1. **Два явні світи в навігації:** «Грати» (ігри, мої заявки, спільноти) і «Матеріали» (новини, статті, системи, набори, довідка).
2. Hero головної: один первинний CTA «Знайти гру» → `/games`, вторинний «Майстрам» (для GM — `/my/games`, для PLAYER — пояснення, що роль дає адмін, або майбутня заявка на GM).
3. Авторизований гравець: у шапці **Мої заявки**; майстер: **Мої столи**; адмін/редактор: **Адмінка**.
4. Каталог ігор: фільтри, які API вже вміє (`status`, система, пошук) + чесні підписи статусів.
5. Пошук: або розширити backend (окрема задача), або в UI явно «шукаємо матеріали, ігри — у каталозі».
6. Спільноти: поки немає членства — підпис «Каталог клубів (вітрина)», щоб не обіцяти Discord-like.
7. Адмінка: пункт «Усі ігри» замість перевантаження «Мої ігри»; статистика blocked/communities якщо вже в API.
8. Мобільне: burger, одна колонка новин, футер стеком.

## 8. Рекомендований порядок перероблення інтерфейсу

Порядок **авторського UI** без зміни бізнес-логіки (кроки з * потребують узгодженого дрібного FE, не нової політики):

1. **Головна + шапка:** ієрархія «стіл / матеріали», CTA на ігри, мобільне меню, порожні стани секцій. Не чіпати auth.
2. **Каталог і картка гри:** фільтри з наявного API*, пояснення статусу, видима кнопка/текст коли набір закрито, учасники.
3. **Кабінет гравця:** пункт «Мої заявки» в навігації; cancel PENDING зі списку* (endpoint уже є).
4. **Кабінет майстра:** чіткіші дії статусу (підписи, попередження перед CANCELLED/FINISHED), прев’ю публічної сторінки.
5. **Пошук і спільноти:** чесні підписи можливостей; не малювати join без бекенду.
6. **CMS-адмінка:** щільність таблиць, прибрати плутанину типу GAME_SYSTEM у content-формі (сховати зайві типи в UI*).
7. **Адмін користувачі:** показати `status` як read-only; block — лише після окремої продуктової політики (не вигадувати в редизайні).
8. **Legal/контакти** — після відповідей власника, не в першій хвилі візуалу.
9. **Нові продуктові фічі** (GM-заявка, leave game, search games, членство спільнот, Discord-поля) — окремий бекенд-етап, не макет «як ніби вже є».

## Додаток C. Відхилення від `docs/UI_HANDOFF.md`

Handoff коректний щодо маршрутів, ролей і контрактів. Уточнення аудиту:

- Пошук у handoff не акцентує, що **ігри не шукаються**.
- «PLAYER: ігри, заявки, профіль, закладки» — заявки **слабко навіговані**.
- Прогалини UX у handoff (банер verify, crop, графіки адмінки) підтверджені; додано: фільтри ігор, leave, GM onboarding, спільноти-вітрина, адаптив шапки.
